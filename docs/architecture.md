# CampusShift architecture (Phase 6 preparation)

The React application requests `GET /api/health`. In development Vite forwards `/api` to FastAPI at `http://127.0.0.1:8000`. An optional `VITE_API_BASE_URL` supports independently hosted frontends. FastAPI allows the configured local browser origins through CORS.

The landing-page status component keeps its mount/manual-retry liveness check. All frontend HTTP calls now use `services/api.js`, which adds in-memory bearer tokens, decodes API errors, times out requests, and supports cancellation. `AuthContext` clears sessions on logout, expiry, or unauthorized responses. Refreshing the browser deliberately requires another login. React Router protects role-specific layouts; backend authorization is authoritative.

SQLAlchemy models and Alembic migrations describe departments, users, recurring class schedules, and recurring availability. SQLite foreign keys are enabled on every connection. Schema creation and demo seeding are explicit commands. Passwords are hashed with Argon2id. JWTs use HS256, issuer/audience validation, required subject/issued-at/expiry claims, and a configured random secret. Responses use schemas that exclude password hashes. Current roles and departments are loaded from the database on each authenticated request, rather than trusted from browser input or token role claims.

Routes validate request/response contracts and call account/window services for persistence. Students address `/students/me` so they cannot select a different owner. Supervisor lookups constrain both role and department, returning 404 for inaccessible employees. Public registration creates only students and permits choosing an existing department for this local phase. Only the explicit seed command provisions demo supervisors; there is no public role elevation endpoint.

Days run Monday (`0`) through Sunday (`6`). Windows are local campus times with minute precision and exclusive end boundaries: adjacent windows are allowed. Same-type overlaps return 409. SQLite writes acquire a write reservation before overlap validation to serialize simultaneous saves. Cross-type class/availability intersections are returned as conflict data without silently adjusting or rejecting either entry. Hour limits are profile values from 0–40; students and their department supervisor can update them. There is no distinction between requested and supervisor-enforced limits yet.

The health endpoint preserves its Phase 1 liveness contract without opening the database. Database-backed routes return a safe 503 on storage errors. Missing or weak signing configuration disables authentication with 503 while leaving liveness usable.

The pure scheduling engine now lives in `scheduler/` and is installed as a local package. The scheduling service adapts department-scoped relational data into typed engine inputs and persists a full draft transactionally. Locations use explicit eligible-student associations. Active staffing demand cannot overlap at one location. The API stores versioned runs, assigned shifts, uncovered periods, input snapshots, and weighted coverage/hour metrics. The initial data-preserving migration adds active scheduling status and a local timezone to the existing models.

The frontend extends the same sidebar, forms, API client and resource/error states with locations, staffing needs, a generator, and filtered weekly draft calendars. Student dashboards expose only personal draft previews; all schedules remain unpublished and immutable after generation. See [scheduling.md](scheduling.md) for constraints, granularity, fairness, local-time policy, versioning and limitations.

Infrastructure belongs in `infrastructure/` so sandbox resources can eventually be recreated. Deployment will require a permitted HTTP entry point and existing sandbox roles; API Gateway, Cognito, and creating IAM roles must not be assumed. No AWS integration is implemented.

Phase 4 extends this design with department-scoped `TimeOffRequest` records and `ScheduleEvent` audit history. Approved all-day leave is added to the existing pure student input. Generation, manual editing and publication share `assignment_error`; fixed assignments share `summarize` for coverage and gaps. Manual edits use SQLite write reservations and required revision checks, with atomic summary/audit updates.

Publication revalidates current constraints, requires explicit acknowledgement of gaps, and atomically archives the previous official version. A partial unique index enforces one published schedule per department/week. Official student views now select only published versions, while Phase 3 draft previews are kept at an explicit unpublished endpoint. Late approved leave creates visible supervisor conflict warnings without modifying published assignments. See [workflows.md](workflows.md) for endpoint contracts, states, audit behavior and limitations.

Phase 5 adds attendance records tied permanently to original assigned shifts, correction proposals and before/after audit events. New attendance timestamps use canonical UTC text with explicit Z through a shared SQLAlchemy type, while published local shift windows convert with ZoneInfo/tzdata and explicit DST policies. Clock actions use server time, owner/published-shift validation and configured eligibility windows. Unique/partial indexes and SQLite write reservations prevent duplicate or simultaneous active clock-ins. Corrections are approved atomically with overlap and record-version validation; pending requests never alter actual hours.

The same API client now supports authenticated CSV text downloads. Student and supervisor attendance pages poll active state, distinguish planned wall-clock hours from actual elapsed hours, show department-local timestamps, expose correction review/audit, and retain attendance on archived publications. No GPS/device collection, wage processing, AWS deployment or notification delivery was introduced. See [attendance.md](attendance.md) for workflow, reporting semantics and endpoint details.

Phase 6 adds PostgreSQL/psycopg support, transaction-scoped write serialization across API workers, UTC database sessions, production settings validation, safe JSON logging and database/migration readiness. Local SQLite remains the default. New CloudFormation templates and TLS/systemd configuration prepare a separate Amazon Linux EC2/RDS + private S3/CloudFront target; no new cloud deployment was executed. See [AWS architecture](aws-architecture.md) and [deployment runbook](aws-deployment.md) for prerequisites, approval gates, fallback and known limits. Existing legacy EC2/SQLite hosting is preserved. Notifications/SNS remain separate unfinished cloud work.
